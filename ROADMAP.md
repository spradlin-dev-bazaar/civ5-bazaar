# Roadmap

What's planned for Bazaar after 0.5. Nothing here has a date, and plans can change. Smaller fixes and ideas are in GitHub's issues.

## The goal

Nobody should have to build one huge DLL mod anymore. The game runs only one mod that replaces its DLL, so big DLL mods have grown to hold everything their authors wanted. Bazaar runs many, so a big mod can be split into plugins, one for each part of the game it changes, such as combat or religion. Players pick the plugins they want and combine them with plugins from other mods. Some plugins from different mods change the same thing and can't work together, and Bazaar tells the player which ones and why.

The plugin API has to be simple enough to use and strong enough that authors of large mods could split their mods into plugins. A ported mod is a handful of plugins, and the mod's options become their settings. Ports come from repositories of their own. Ports that Bazaar's own team makes, such as moving VMC into plugins, keep each feature's spirit, not a draw-for-draw match with the original.

## How releases work

Any 0.x release may break plugins and saves. A release that does comes on a new Steam Workshop item, and the old item stays up, so a game started on it plays on there to the end. Nothing ever converts an old save or keeps an old API working. A breaking release gathers several breaking changes at once, so players and plugin authors move to a new item only now and then. Each release below says whether it breaks, and why its changes land together.

## 0.5: out now

Bazaar 0.5.0 is the first public release.

## 0.6: what every port needs

**0.6 breaks plugins and saves.** It changes the shape of every hook, the order after-hooks run in, the save file and how culture and faith are kept, and adds the block of data each plugin carries. These all change what a plugin is built against or what a save holds, so they land together and plugins are rebuilt once.

- **Hooks that change the call** ([#116](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/116), [#117](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/117)). A before-hook gets the values the game's function was called with, by reference, so it can change them, and everything after it sees the change. An after-hook gets a record of the call: whether a before-hook vetoed it, and a slot where a before-hook of the same plugin can leave a value for it. The record belongs to that one call, so it is right when a function runs again before it returns. After-hooks run in load order, as before-hooks do, so a plugin loaded after another sees that one's changes with both kinds of hook. After a veto, after-hooks still run, and the record says so.
- **Each plugin describes itself** ([#120](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/120), [#83](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/83)). A plugin carries a block of data that Bazaar reads before running any of its code, as it reads the API version today: the plugins it needs, the plugins it can't work with, its settings, and the names it owns. Bazaar loads a plugin after the plugins it needs and holds it back when one of them doesn't run, saying which. Of two plugins that can't work together, the lower in the list sits out; either author can list the clash, and a clash can name one of the plugin's settings, so only that setting is switched off for the game. Bazaar finds plugins by this block: every DLL in an active mod that carries one is a plugin, known by its mod and its file name, so two mods can ship DLLs with the same name. When plugins form a loop, each wanting to load after another, Bazaar keeps the player's order and names the loop. Once every plugin has loaded, Bazaar tells each one, so it can look for plugins it can use but doesn't need.
- **Plugin settings** ([#84](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/84)). A setting has a name, a kind (on or off, a number, or a choice), a default and a line of help, and is known by its plugin and its name, so two plugins' settings never collide. Players change settings on the Plugins screen when they set up a game, and the game keeps them for its whole life. When a plugin registers a hook, it can name the setting the hook belongs to: Bazaar runs the hook only in games where the setting is on, so a replacement for a feature that's off clashes with nothing. When two plugins replace the same function in a game, Bazaar holds back the lower one: its setting is switched off for that game if the replacement has one, otherwise the plugin sits out the game. The Plugins screen says which and why before the game starts. A mod can say it needs a setting, with a row in its SQL; the Plugins screen sets it, names the mod, and the player can't change it while the mod is on. Settings belong to the game, not the computer: a plugin that needs something per computer, such as a port number, keeps a file of its own.
- **Saves own their plugins** ([#121](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/121)). A saved game owns its plugin list, order and settings. Bazaar writes them into the save's setup part, which the game reads before anything else, so the hooks for that game are in place before the game's data is read. Loading a save sets the player's list to match, and one message names what changed. If a plugin the save needs isn't installed, the save doesn't load, and Bazaar names it. If a plugin was updated since the save, the game's own `MinCompatibleSaveVersion` in the plugin's mod decides whether the save loads; the guide tells authors to raise it when their saved data changes in a way older saves can't be read. A plugin installed after a game started isn't part of that game.
- **Plugin tables** ([#119](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/119)). A plugin keeps its rules in tables of its own in the game's database, one row per building, unit, policy and so on, under names that start with a tag of the plugin's. The SDK adds a helper that reads such a table into lookups by the game's own numbers, and the guide a section. Other mods add rows to a plugin's tables with XML or SQL, as they do to the game's own, and load after the plugin's mod. A plugin reads its tables in its entry function, and Bazaar loads plugins afresh each time the game rebuilds its database, so what a plugin read is always current.
- **A moment for when a game is ready** ([#123](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/123)). A hand-placed announcement once a new game is set up or a saved game has loaded, when the map and every player exist. A plugin that works something out from the map or the players does it there, and rebuilds totals instead of adding to them, since some of the game's setup runs more than once.
- **Culture and faith in hundredths** ([#140](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/140)). The game keeps gold, production and science in hundredths, but rounds each city's culture and faith down to whole numbers every turn, so a +25% bonus on 3 culture does nothing. Culture and faith will be kept in hundredths too, and the fractions are kept. This is the one change to play that Bazaar's core makes on purpose. The game's Lua methods keep giving whole numbers, and new ones give hundredths.
- **The private and protected parts of the game's classes** ([#85](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/85)). Code moved out of a big mod uses them everywhere.
- **Crash reports players can send** ([#82](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/82), [#56](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/56), [#124](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/124)): a readable report for every crash, with the whole call stack. Bazaar's debug file ships in the SDK, so an author's debugger and crash call stacks name the game's and Bazaar's functions too.
- **Bazaar's calls placed by its build tools** ([#79](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/79)). Bazaar adds calls of its own into the game's code; its build tools will place them, as they place hooks today. 0.7's hooks inside functions build on this, and it lets other DLL mods include Bazaar.
- **A replay check** ([#111](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/111)). The game plays out the same way twice from the same start and seed. A test plays a game with AI players only, records every random number drawn and a summary of each turn, and compares two builds of Bazaar, to prove that a change to the game's code alters nothing in play. Before it's trusted, one build runs twice and must match, and one planted extra draw must be caught. It proves 0.7's splits and speed fixes; ports aren't held to it.
- **VMC code that changes play while its option is off** ([#108](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/108), [#112](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/112), [#113](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/113), [#114](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/114)). Some of VMC's options are off by default but still change play: ranged units and cities can't fire at a submarine under ice; a random number is drawn for every unit created; a new Great Admiral can be left in a city on a lake; only enemy ships blockade a city's worked water tiles. Each will check its option, so that while it's off it changes nothing. The six bugs the survey found in VMC's code ([#104](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/104) to [#109](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/109)) are fixed too.
- **Two bugs in the game's own code** ([#141](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/141), [#142](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/142)). Game options whose names start the same way read and overwrite each other's values, and city-states in player slots 32 and above share each tile's trade-route marks with other players. Both are fixed.
- **Multiplayer: a first try** ([#115](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/115)). Play a multiplayer game and a hot seat game with Bazaar and no plugins, on a test build whose mods say they support both. If this fails in ways Bazaar can't fix, multiplayer stays out, and the releases before 1.0 know early.

## 0.7: smaller pieces of the game's code

A plugin can replace a whole function of the game's code, or add to its start or end. Big mods often change a line or two in the middle of a long function, so two plugins that change different lines of the same function can't both run.

**0.7 breaks saves and some plugins.** VMC's first features leave Bazaar's core and become plugins, so their saved data moves and a plugin that called the code that moved needs rebuilding. The splits break nothing: the original functions stay and call the new ones.

- **The longest functions split** ([#125](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/125)) into smaller ones, each of which a plugin can hook or replace on its own. What the game does doesn't change, and the replay check proves it. The survey lists the splits for the 60 functions mods change most, such as the reward from a goody hut, the steps of a battle and a city's turn. Where a function ends by rounding or clamping a number, the smaller function ends just before that line. Copies of the same code become one function. A plugin that replaces a whole function skips the hooks on its pieces, so that counts as a clash with the plugins that hook them, as replacing a function with a hand-placed hook inside does today.
- **Hooks inside functions** ([#126](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/126)) where mods need them, listed in a file beside the hook generator and placed by the build tools. Each gets the function's working values, such as a battle's damage before it's applied, so a hook can change them. Today's hand-placed hooks join the list. One example: the AI picks each strategy's test by name from a fixed list, so a strategy a mod adds is never tested; a hook before that list lets a plugin test its own. Where a port needs to know each time the game changes a value, the value gets a function that sets it.
- **Functions in the game's header files** ([#127](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/127)). These can't be hooked today. The ones mods change will be moved where they can be, starting with the one that gives how many units fit on a tile, after measuring what a hook on the pathfinder's path costs.
- **Numbers that explain themselves** ([#128](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/128)). Tooltips work out their numbers again with copies of the game's calculations. When a function that works out a number is split, it also writes the lines that explain the number, and the tooltip asks it instead of repeating it, so a plugin that changes the number changes its line in the same hook.
- **Speed, measured** ([#129](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/129)) with plugins that hook the game heavily, and Bazaar's own costs made smaller where they matter. Speed fixes from other mods go into Bazaar's code only where measuring shows they're faster and the replay check shows they change nothing. The measurements also decide whether values are fast enough for ports with thousands of fields.
- **Several plugins in one mod** ([#131](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/131)). The SDK's template builds and releases one plugin; a port builds and releases all its plugins together, as one mod.
- **VMC's first move** ([#138](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/138)). VMC's features that need only what 0.6 and 0.7 give leave the core, grouped into plugins by part of the game, such as units and promotions, movement and the map, and religion. Each feature becomes a setting with its VMC option name. A mod that switches the option on with a row in VMC's options table keeps working: Bazaar reads the row as that mod needing the plugin's setting, and Lua's `Game.IsCustomModOption` answers from the game's settings. Until a feature moves, Bazaar's core reads its option as today. Until 1.0, VMC's plugins ship inside Bazaar's own mod, so a player with mods made for VMC, including whoward69's pick'n'mix mods, has nothing to change. This is the first port, made with Bazaar's own code, so the tools are tried before anyone else needs them.

## 0.8: data and Lua

**0.8 doesn't break.** Everything here adds to what plugins can use.

- **More kinds of values** ([#132](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/132), [#133](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/133)). Values are a plugin's own saved data on players, cities, units and plots. They will also sit on teams and on the game as a whole, hold lists, and take a number key for things inside an object, such as a player's spies. Whether a value can also hold a plugin's own struct is decided after 0.7's measuring and a count of what kinds of fields the big mods add.
- **Lua for plugins** ([#134](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/134)). Plugins add Lua methods to players, cities, units, plots and teams, as the game's own are; the hooks for it exist today, and the SDK gets a helper and the guide a section. When two plugins add a Lua function or method with the same name, the Plugins screen says so. A plugin fires events through `GameEvents`, as VMC's do, so Lua mods listen the way they already do. The game program keeps the listener lists and gives Bazaar no way to count them, so a plugin puts an event that fires often behind one of its settings, as VMC's event families sit behind options, and a Lua mod that needs the event says so. Each event name belongs to one plugin, named in its block and starting with the plugin's tag, and the names the game and VMC fire are reserved.
- **New entries in the game's built-in lists** ([#135](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/135)). The game numbers some kinds of thing in lists written into its code, such as city tasks, trade items and quest types. Each such list becomes a table in the game's database, with the game's own entries first. A plugin's mod adds an entry as a row, and each row names the plugin that handles it. Bazaar numbers the new entries itself, after the game's own, and keeps the numbering in the save, so an entry keeps its number for the life of a game; a save that uses an entry that no longer exists doesn't load. Where the game's code handles the list one entry at a time, an entry it doesn't know goes to a hook inside that function, named for what the place decides, such as "can this be traded", and the plugin named on the row answers. VMC's city-state quests already work this way and become one of these tables. Lists are converted one at a time, after reading the code that uses them, because some of it uses a list's count to mean "none". Lists the game program handles itself, such as interface modes, pop-up types and trade-route kinds, stay on the slots Firaxis left for modders.
- **A trade screen for plugins' trade items** ([#136](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/136)). The game's trade screen names its 14 trade items by hand, and its list of what's in a deal skips an item it doesn't know. So Bazaar ships its own copy of the game's trade screen as a separate mod, changed in two ways only: it loads a file from each plugin that adds a trade item, and it shows any item in a deal by its name. The declare-war pop-up gets the same fallback. Plugins that add trade items need this mod, and a general Lua method lets a screen put a plugin's item into a deal.
- **A second port.** A few pieces of a big mod whose license lets anyone reuse its code, that between them use tables, list entries and Lua methods, to try the tools on code Bazaar didn't write.

## 1.0: a clean core

Bazaar 1.0 is the release where Bazaar becomes a clean base with no gameplay changes of its own, apart from keeping fractions of culture and faith, and where big mods can be fully ported. It keeps the game's own code and what mods made for VMC rely on: VMC's Lua events, its options table, and the functions VMC added for numbers the game had fixed, such as a unit's maximum health, a city's working radius and how many units fit on a tile. Plugins hook those functions to change the numbers.

**1.0 breaks plugins and saves.** The layout of the game's classes changes for yields, and the last of VMC's code leaves the core. Every plugin is rebuilt for 1.0. After 1.0, breaking releases may become rarer, but nothing is promised.

- **The rest of VMC moves** ([#138](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/138)). The features that waited for 0.8 leave the core, into the same plugins by part of the game. VMC's bug fixes that don't change play, such as crash fixes, stay in Bazaar; those that change play go into a plugin, each with a setting. Bazaar's core keeps the name of every Lua method VMC added: when the plugin that owns it runs, the method passes the call on; when it doesn't, the method answers as if the feature is off, so a Lua mod made for VMC doesn't stop with an error. From 1.0, VMC's plugins come on their own Workshop item, and whoward69's original pick'n'mix mods are all blocked at once, since VMC's plugins and their settings replace them. The plugins come from one repository, are released with each Bazaar release, and each feature is checked in the game before 1.0 ships.
- **Yields plugins can add** ([#139](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/139)). Yields are a list too, but their count sets the size of lists inside the game's classes, so room for more changes the layout. 1.0 is built with room for more yields, and a plugin's mod adds one as a row, numbered by Bazaar like any other list entry. Loops over yields run over the ones the game uses, not the spare room. How much room comes from measuring, since the yield lists sit in the game's busiest code.
- **More than 22 major civilizations, if a test allows it** ([#139](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/139)). The DLL has 63 player slots shared by major civilizations and city-states, so more majors would take city-state slots, but the game program is built for up to 80 players. A test build with more slots plays a game with more than 64 players, then saves and loads it. If that works, a breaking release builds Bazaar with room for more majors in the new slots. Games still allow 22 unless a mod raises the limit, the same way a mod adds a yield. If not, it isn't planned.
- Bazaar 1.0 comes on new Steam Workshop items, and its Workshop page links to the new plugins.

## After 1.0: multiplayer and hot seat

This is [#51](https://github.com/spradlin-dev-bazaar/civ5-bazaar/issues/51). Until it's done, Bazaar and its plugins are single player only. It comes after 1.0 so it's built once, on the clean core, with 0.6's first try telling us early whether it can work.

1. Players get a way into multiplayer games with mods, since the game hides its own button for them, and the multiplayer and hot seat setup screens lead to the Plugins screen.
2. Every player's computer gets the game's plugin list, order and settings from the host, as it gets the game's options today.
3. Plugins send commands of their own to every player's computer through one channel Bazaar owns. Mods today hide such commands inside the game's own messages, such as the one for renaming a city, and two mods that do this clash without any warning.
4. A plugin crash on one computer stops the game for everyone and points to the last autosave. The crash pop-up isn't lost in hot seat when the turn passes.
5. Mark Bazaar, and the templates new plugins and Lua mods start from, as working in multiplayer and hot seat.

After that: a list of plugins that players can share, which also tells them which mods they still need.

## Not planned

- **Running another mod's whole game DLL beside Bazaar.** Only one mod can replace the game's DLL. The way to combine big DLL mods is to split them into plugins, as above. A big mod could also build Bazaar into its own DLL, but that would be their own build of it.
- **More than one plugin replacing the same function.** Bazaar holds one back and the Plugins screen says why. Hooks before and after a function, which any number of plugins can add, cover most needs, and 0.7's smaller functions cover more. In every case the survey found of two mods replacing the same function, neither runs the game's original, so letting both run would still lose one.
- **Keeping old API versions or converting old saves.** A breaking release comes on a new Workshop item, and the old one stays up for the games started on it.
- **Bazaar's own copies of the game's screens,** such as the combat preview or the tooltips: Bazaar would clash with every UI mod that replaces the same screens. Instead, 0.7's split functions write their explaining lines, and 0.8's Lua for plugins hands them to any screen that asks. The one exception is the trade screen, which can't show a plugin's trade item any other way.
- **Settings that belong to the computer.** A setting belongs to the game and is saved with it. A plugin that needs something per computer keeps a file of its own.
- **Hooking another plugin's functions.** A plugin that wants others to change its own work publishes a function they can register with, as plugins publish functions today.
- **Checking that a port plays draw for draw like the original.** Ports keep a mod's spirit, and each ported feature is checked in the game.
- **A newer Visual Studio.** The game was built with Visual Studio 2008 and passes text to Bazaar in the form that version uses, so Bazaar and its plugins stay on 2008.
